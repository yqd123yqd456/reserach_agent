# trace_viewer 速查卡：拿到题后怎样开工

> 配套：[Knowledge/trace_viewer](../../Knowledge/trace_viewer/README.md)、[Practice/trace_viewer](../../Practice/trace_viewer/README.md)。

## 开工顺序

1. **先看数据，不写界面**（20–30 分钟）：用 Python 加载，回答：有几条 run？每条有哪些事件类型？调用和返回靠什么字段关联？有没有时间戳、嵌套、评分、状态？哪些字段缺失或不一致？
2. **写下用户 journey**（3–5 步），它就是验收清单。
3. **写标准化脚本**：原始日志 → run 摘要列表 + 每条 run 的步骤序列。配对、排序、异常打标都在这里，并配断言测试。
4. **做最小页面**：一个状态对象、三栏、每次交互重新渲染。先让第 1 条 journey 走通，再加筛选、搜索、对比。
5. **用无头浏览器或手工按 journey 走一遍**，记录结果。
6. README：怎样打开、支持哪些调查动作、对不完整日志怎样处理、不支持什么。

## 技术选择（JS 基础较少时）

- 单个 HTML 文件 + 原生 JavaScript，数据用 `<script src="data.js">` 加载。不需要构建工具，不需要后端，评审者双击就能打开。
- 数据处理尽量放在 Python。页面只做筛选、选择、显示。
- 题目明确要求某个框架时再用。允许使用 AI 工具时，让它生成界面代码，自己负责数据层、状态设计与验收。

## 必须能回答的问题

- 调用没有结果、结果没有调用、乱序、重复、截断，各自怎样显示？为什么不丢弃？
- 列表页读的是什么数据？打开一条 run 时又读什么？数据量大 100 倍会先在哪里出问题？
- 研究员怎样从“某个检查失败”走到“哪一步造成的”？
- 两条 run 的“第一次不同”说明了什么，不说明什么？
- 这个工具没有显示什么？（状态的中间过程、被截断的内容、模型的完整输入）

## 常见错误

- 一上来就搭前端框架，数据层没有测试。
- 在界面代码里做配对与修补，同样的逻辑散落在多处。
- 悄悄丢弃配不上的记录，或者悄悄修好乱序。
- 只显示对话，不显示评分证据与状态变化。
- 把完整轨迹全部渲染出来，长 run 打不开。

## 自测（闭卷）

1. Inspect 的一次工具调用，在数据里靠哪个 id 把三样东西关联起来？是哪三样？
2. `.eval` 文件为什么把样本摘要和完整样本分开存？
3. 用 Python 的话说明：组件、状态、派生数据分别是什么。
4. Inspect viewer 怎样拿到运行中样本的新事件？
5. 草图里 `run-messy-log` 的 5 种日志异常分别是什么？

<details><summary>参考要点</summary>

1. tool call id：assistant 消息里的调用、工具事件、tool 结果消息。
2. 列表只需要摘要，避免加载全部轨迹；增量写入的摘要与 journal 让运行中或崩溃的日志也可读。
3. 组件：输入数据、返回界面描述的函数。状态：一个 dict，变化后重新渲染。派生数据：由状态和数据算出、不单独保存的值，可缓存。
4. 轮询：带版本标记请求样本列表，带“上次读到的事件 id”请求新事件。
5. 写入乱序、输出截断、结果重复、孤儿结果、调用缺结果。
</details>
