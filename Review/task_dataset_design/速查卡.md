# task_dataset_design 速查卡：拿到题后怎样开工

> 配套：[Knowledge/task_dataset_design](../../Knowledge/task_dataset_design/README.md)、[Practice/task_dataset_design](../../Practice/task_dataset_design/README.md)。

## 开工顺序

1. **把能力描述写成一句可检验的话**：在什么环境、给什么信息、做到什么算成功。列出这句话**不**覆盖的情况。
2. **先做一个任务做到底**，再考虑数量：fixture → 实际运行确认症状 → 指令 → oracle 解 → 隐藏 verifier。
3. **写 verifier 时逐条问**：这个判定用到了被测代码提供的数据、指标或打印值吗？用到了就换成自己的。
4. **审计**：no-op、两个写法不同的合法解、每条想得到的捷径，各跑一遍；填审计表。
5. **再扩展成族**：同一类 bug 的不同实例、不同类 bug；记录来源、难度依据、族；按族划分 dev／test。
6. README 写清：能力声明、任务数与族数、审计结果、已知局限、未做的验证。

## 必须能回答的问题

- 什么都不做能通过吗？硬编码输出呢？改测试呢？
- 有几种合法解？verifier 判的是行为还是实现？
- 指令里没说、verifier 却依赖的东西有哪些？
- 这个任务失败，是模型不行还是题有问题？用什么证据区分？
- 一个任务的通过率能支持“模型会修训练 bug”吗？需要什么样的任务集才行？

## 常见错误

- 症状描述没有实际运行过。
- 可见检查与隐藏判定用同一套逻辑（agent 可以针对它优化）。
- verifier 调用被测代码自己的评估函数。
- 约束只写在指令里，verifier 不检查（例子里的“保留打乱”）。
- 任务随机划分，近重复跨越 dev 与 test。
- 难度按模型通过率事后定义。

## 自测（闭卷）

1. 例子里带 bug 的代码在 seed 0 上准确率 0.995。为什么？这说明可见检查应该怎样设计？
2. “删除打乱”能让模型学会，为什么仍判为错误修复？verifier 怎样发现它？
3. Terminal-Bench 为什么在 agent 结束后才把测试复制进容器？
4. 给出两个信号，说明一次失败更可能是题目问题。
5. dev 与 test 为什么按族划分？

<details><summary>参考要点</summary>

1. 标签错位后权重只剩噪声，方向随机；seed 0 恰好方向正确。可见检查要用多个 seed 与多个指标；更重要的是不能把它当判定依据。
2. 违反了任务明确要求的约束。verifier 用同一份数据、不同 seed 训练两次，权重相同说明打乱已不存在。这只检查“结果依赖 seed”；“每个 epoch 都重新打乱”要靠记录样本的读取顺序来判（`constraint.reshuffles_each_epoch`），它的已知缺口见 Knowledge §8。
3. 防止 agent 读取或修改测试与参考答案。
4. oracle 解不通过；多个强模型在同一断言上失败且轨迹合理；专家认为指令不充分。
5. 族内任务高度相关，随机划分会让近重复同时出现在两边，test 上的表现高估泛化。
</details>
