# 准备不足情况下的 12 小时 AI-assisted take-home 执行指南

> 更新于 2026-11-14。**正式做题时先打开这个文件。**
> 这是执行手册，不是知识综述；知识在各专题里，这里只给做法和指向具体文件的链接。
>
> **优先级**：正式题目、交付要求、AI 使用规则 > 本指南。12 小时是准备假设；时限不同时按比例缩放，阶段顺序与验收不变。规则限制 AI 的部分，按规则办，本指南对应内容作废。
> 六个方向是按 JD 推断的可能题型，不是已知考题。题目落在它们之外时，§1、§3–§7 仍然适用。

## 怎样用这份指南

| 时刻 | 看哪里 |
|---|---|
| 拿到题目 | §1（前 60 分钟）→ 把 §7 的 prompt 填好发给 Claude |
| 确定题型后 | §2 里对应的那一张卡，只读那一张 |
| 做题过程中 | §3（现在该在哪个阶段、落后了砍什么）；§4（这一阶段你要确认什么） |
| 卡住时 | §5 |
| 最后 2 小时 | §6 |

## 1. 前 60 分钟

目标：60 分钟结束时，手里有一句话的最小交付、3–5 条验收、一条已经确认能跑的环境。**这一小时不写功能代码。**

| 时间 | 做什么 | 产物 |
|---|---|---|
| 0–10 分 | **通读题目两遍**。第二遍标出三类句子：必须做的（“must”“需要”“请提交”）、评分看什么、限制（时限、语言、工具、AI 规则、提交格式） | 一张“硬性要求”清单，逐条抄原文 |
| 10–15 分 | 把 §7 的 prompt 填好发给 Claude，让它**只读不写**：列目录、读说明文件、探查数据与环境 | Claude 的探查报告 |
| 15–30 分 | 对照探查报告核实：数据有多少条、什么格式、有没有缺失与不一致；给的代码能不能跑；需要哪些依赖、API、密钥；本机环境是否满足（命令见[附录 A](#附录-a前-60-分钟的探查命令)） | 数据概况表；“环境能跑／不能跑、缺什么” |
| 30–40 分 | **写验收条件**：从硬性要求出发，每条写成可执行的检查（“运行 X，得到 Y”）。分成“必须”与“加分” | 3–5 条“必须”验收 |
| 40–50 分 | **定最小端到端路径**：一个输入，从读入到产出最终结果，中间每一步用最简单的实现。对照 §2 找到最接近的方向卡 | 一句话：“输入 __，运行 __，得到 __，由 __ 证明正确” |
| 50–60 分 | 写“不做”清单与理由；把 §3 的时间表按实际时限缩放；有不清楚的规则就**现在**问出题方 | 范围表；时间表；待确认问题 |

**识别硬性要求时最容易漏的**：提交格式（仓库、压缩包、文档）；是否要求可复现的运行命令；是否要求真实模型调用；是否限制依赖；是否要求说明 AI 的使用方式。

**60 分钟时自查**：我能不能不看题目，说出“要交什么、怎样算对、什么不做”？不能就再花 10 分钟，不要带着模糊的目标开工。

## 2. 六个方向的开工卡

每张卡互相独立。**不要假设必须把几个方向组合成一个项目**；题目跨方向时，选一个作主线，其他只做到主线需要的程度。

### 2.1 grading：写判分逻辑

| 项 | 内容 |
|---|---|
| 典型输入 | 一批模型输出 + 评价标准（文字或半结构化）；有时附可信的运行日志或参考答案 |
| 典型输出 | 判分脚本；每个样本的逐项结果与证据；聚合报告；grader 自身的测试 |
| 第一条端到端路径 | 一个样本 + 一条能用代码判定的标准 → 一条带证据的检查结果 → 打印出来 |
| 最小模块 | 加载 → 解析／归一化 → 检查项列表（每项一个函数）→ 样本汇总 → 聚合 → audit |
| 核心正确性检查 | 六类样例与人工期望标签比较：正确、局部错误、等价正确、欺骗性、解析失败、缺失输出。误接受为 0 |
| 可以砍 | LLM judge（改为“此项需要 judge，未实现”，状态记 unknown）；strict／loose 双模式；部分得分；漂亮的报告 |
| 不能砍 | 缺失与解析失败的固定规则；unknown 不当通过；至少一个欺骗性样例 |
| 先读 | [`Review/grading/速查卡.md`](../grading/速查卡.md) → [`Practice/grading/sketch/grade_report.py`](../../Practice/grading/sketch/grade_report.py)（约 150 行，直接当骨架）→ 主文 [§5](../../Knowledge/grading/README.md#5-strictloose部分得分与各种判不了) |

### 2.2 task_dataset_design：设计评估任务

| 项 | 内容 |
|---|---|
| 典型输入 | 一句能力描述，或一批原始材料（bug、PR、论文） |
| 典型输出 | 任务定义（指令、初始代码与数据、预算）、隐藏 verifier、任务审计表 |
| 第一条端到端路径 | 一个任务：初始代码 → **实际运行确认症状** → 指令 → 参考解 → verifier 接受参考解、拒绝原始代码 |
| 最小模块 | 任务定义文件；fixture 目录；verifier；审计脚本（对若干候选解跑 verifier） |
| 核心正确性检查 | 审计表：什么都不做 → 拒绝；两个写法不同的合法解 → 接受；至少三条捷径（硬编码输出、特判可见输入、改评估）→ 拒绝 |
| 可以砍 | 任务数量（一个做透好过五个粗糙的）；难度标定；数据划分；容器隔离（写进局限） |
| 不能砍 | verifier 用自己的数据与指标实现，不信任被测代码打印的数字；症状描述来自实际运行 |
| 先读 | [`Review/task_dataset_design/速查卡.md`](../task_dataset_design/速查卡.md) → [`Practice/task_dataset_design/sketch/`](../../Practice/task_dataset_design/sketch/) 的 `verifier.py` 与 `audit_task.py` → 主文 [§7 审计表](../../Knowledge/task_dataset_design/README.md#7-任务审计表每个任务填一张) |

### 2.3 trace_viewer：把日志做成能调查的工具

| 项 | 内容 |
|---|---|
| 典型输入 | 一批 run 的日志（JSON／JSONL，格式可能陌生、可能不完整）+ 评分结果 |
| 典型输出 | 一个能打开的小工具；数据标准化脚本；支持哪些调查动作的说明 |
| 第一条端到端路径 | Python 读一条 run → 标准化成步骤列表（调用与返回配对）→ **先打印成文本时间线** → 再做页面 |
| 最小模块 | 标准化脚本（Python，带断言）→ 数据文件 → 单个 HTML（一个状态对象 + 渲染函数）→ 检查脚本 |
| 核心正确性检查 | 标准化的断言测试（配对、乱序、缺失、重复、孤儿）；页面按用户 journey 走一遍的**带断言**的检查 |
| 可以砍 | 页面本身（退到命令行文本时间线 + 筛选参数，功能等价）；搜索；双 run 对比；样式；实时刷新 |
| 不能砍 | 配不上的记录保留并打标，不丢弃；评分证据与轨迹能对应起来 |
| JS 较弱时 | 数据处理全部放 Python；页面只做筛选、选择、显示；让 Claude 写页面，你审数据层与验收。读页面代码时用 [Practice §4 的 Python 对照](../../Practice/trace_viewer/README.md#4-怎样读这段-javascript给-python-背景) |
| 先读 | [`Review/trace_viewer/速查卡.md`](../trace_viewer/速查卡.md) → [`Practice/trace_viewer/sketch/normalize.py`](../../Practice/trace_viewer/sketch/normalize.py) → `viewer.html` 的 `<script>` 部分 |

### 2.4 training_eval_diagnostics：诊断训练与 checkpoint

| 项 | 内容 |
|---|---|
| 典型输入 | 训练日志；若干 checkpoint 的评估结果（按任务、按试验）；部分输出样例 |
| 典型输出 | 诊断报告（什么变了、哪些可信、可能的解释、下一步验证）+ 生成它的脚本 |
| 第一条端到端路径 | 两个 checkpoint → 确认它们可比 → 同一批任务上的配对差与区间 → 一句结论 |
| 最小模块 | 加载与关联 → 可比性检查 → 任务级通过率 → 配对比较 → 分切片 → 下钻到样本 |
| 核心正确性检查 | 可比性检查的断言（版本不同、任务集合不同、无效试验）；在一个你知道答案的小构造数据上，脚本给出正确结论 |
| 可以砍 | 图表（文本表格即可）；自动报警；全部切片（先做最大的几个）；因果实验（写成“下一步”） |
| 不能砍 | 可比性检查；统计单位是任务；无效试验单列；至少读过几个具体样本 |
| 先读 | [`Review/training_eval_diagnostics/速查卡.md`](../training_eval_diagnostics/速查卡.md) → [`Practice/training_eval_diagnostics/sketch/diagnose.py`](../../Practice/training_eval_diagnostics/sketch/diagnose.py) → 主文 [§5 固定路径](../../Knowledge/training_eval_diagnostics/README.md#5-机制诊断的固定路径) |

### 2.5 agent_failure_investigation：用 agent 帮忙调查失败

| 项 | 内容 |
|---|---|
| 典型输入 | 很多条 rollout、评分、环境错误记录 |
| 典型输出 | 失败类别与占比、代表案例、证据位置、竞争假设、人工复核队列；以及对这套方法可靠性的评估 |
| 第一条端到端路径 | 代码规则先分诊一类最明显的失败（例如环境错误）→ 每条结论带 `(run, 步骤, 原文引用)` → 校验器确认引用存在 |
| 最小模块 | 结构化摘要 → 规则分诊 → 只读调查工具 → 结论 schema → 引用校验器 → 评分脚本（对照预置真值） |
| 核心正确性检查 | 引用校验（编造的引用被拒）；一个小的评估集：已知故障、无故障对照、过程有噪声的成功 run；分别报告证据有效率、误归因、漏检、对照组误报 |
| 可以砍 | LLM／agent 本身（先交规则基线 + 工具 + 评估框架，agent 写成“下一步”）；聚类；多 agent |
| 不能砍 | 证据绑定与校验；“不确定”是合法输出；有对照组 |
| 先读 | [`Review/agent_failure_investigation/速查卡.md`](../agent_failure_investigation/速查卡.md) → [`Practice/agent_failure_investigation/sketch/inv_tools.py`](../../Practice/agent_failure_investigation/sketch/inv_tools.py) 与 `score_assistant.py` → 主文 [§6 workflow](../../Knowledge/agent_failure_investigation/README.md#6-最小-workflow有边界的单-agent) |

| 项 | 内容 |
|---|---|
| 典型输入 | 一个现成的实验／研究自动化仓库 + 一句开放要求（“改进它”“让它更可靠”） |
| 典型输出 | 对真实机制的说明；一个范围明确的改动（代码 + 测试）；证明它有用的证据 |

## 3. 12 小时时间预算

功能开发（阶段 2、3、5）合计 5.5 小时，不到一半。其余给理解、调试、验证、复跑、文档与演示。

| 阶段 | 时间 | 产物 | 验收（达到才进入下一阶段） | 落后时怎样缩 |
|---|---|---|---|---|
| 0 读题与定范围 | 0:00–1:00 | §1 的全部产物 | 最小交付是一句话；3–5 条验收；环境确认 | 不缩。这一小时省不得 |
| 1 骨架与数据合同 | 1:00–1:45 | 目录结构；输入输出的数据格式；一个手工写的样例输入与期望输出 | 你能说出每个字段为什么存在 | 字段只留最小路径用到的 |
| 2 第一条端到端路径 | 1:45–4:00 | 一个输入走完全程；一条运行命令 | 命令能跑；输出与手工期望一致 | 中间步骤用最笨的实现；外部依赖先用替身（见 §5） |
| 3 扩到全部输入 + 异常处理 | 4:00–6:00 | 全量数据能跑；缺失、解析失败、无效输入各有固定规则 | 每种异常一个样例，行为符合写下的规则；不崩溃 | 只处理数据里真实出现的异常，其余写进局限 |
| 4 验证 | 6:00–7:45 | 带断言的测试；反例；至少一个反向验证；（判分类）audit；（比较类）区间 | 测试失败时以非零状态退出；反向验证确实失败 | 保留“一个正例、一个反例、一个反向验证”，其余砍 |
| **调试缓冲** | 7:45–8:30 | — | 阶段 2–4 的验收全部成立 | 这段时间本来就是给超支用的；没超支就提前进入阶段 5 |
| 5 一个加分项 | 8:30–9:30 | 范围表里排第一的那项 | 同样有命令、输出、检查 | **落后时整段砍掉** |
| 6 干净环境复跑 | 9:30–10:15 | 在新目录（新克隆或解压提交包）里按 README 从头运行一遍 | 不依赖你机器上的残留文件、缓存、环境变量；结果与之前一致 | 至少跑主命令与测试 |
| 7 README | 10:15–11:00 | 按[附录 D](#附录-dreadme-模板) 写 | 每个数字对得上一条命令；“未运行”清单完整 | 设计说明缩成要点；局限与未运行清单不能缩 |
| 8 演示与 code review 准备 | 11:00–11:45 | §6 的清单；一条演示路径讲一遍并计时 | 你能不看稿讲完；能回答[附录 C](#附录-c理解检查题库) 里本题相关的问题 | 只练“数据流”和“一次失败及修复”两段 |
| 9 最终检查与提交 | 11:45–12:00 | 提交 | 提交物符合题目要求的格式；提交后再打开确认一次 | — |

**三个检查点**（到点不达标就立刻缩范围，不加班赶原计划）：

| 时间 | 应当已经有 | 没有时 |
|---|---|---|
| 4:00 | 一条端到端路径 | 把最小交付再砍一半：更少的输入类型、更少的检查项、用替身 |
| 7:45 | 测试与一个反向验证 | 砍阶段 5；阶段 3 没做完的异常处理写进局限 |
| 10:15 | 干净环境复跑通过 | README 里如实写出哪条命令在干净环境失败、原因是什么 |

**缩减顺序**（从上往下砍）：加分项 → 界面与图表 → 第二种输入格式 → 真实模型或 judge 调用（题目未强制时）→ 异常处理的覆盖面。
**不缩减**：一条端到端路径；至少一个反例与一个反向验证；干净环境复跑；README 的局限与未运行清单。

每小时记一行进度（模板见[附录 E](#附录-e进度记录模板)）。

## 4. Claude 和你的职责

### 4.1 分工

| | Claude | 你 |
|---|---|---|
| 实现 | 写全部代码，包括核心逻辑、policy、verifier、测试 | 不需要逐行读；抽查关键函数 |
| 运行与调试 | 运行、读报错、修复、重跑；每次给出命令与**实际**输出 | 看输出是否与你的预期一致 |
| 设计 | 每阶段先用几句话讲设计，再动手 | **确认或修改**；不理解就问到理解为止 |
| 验收 | 把验收条件写成可执行的检查 | **决定**验收条件是什么；确认检查真的在检查它 |
| 规则 | 实现规则；指出规则没覆盖的情况 | **理解并认可**每条关键规则（什么算通过、什么算失败、判不了怎么办） |
| 证据 | 提供命令、输出、反向验证 | **亲眼看**证据；至少亲手运行一次主命令 |
| 取舍 | 列出选项与代价 | **拍板**做什么、砍什么 |
| 文档与讲解 | 起草 README；按你的要求解释任何部分 | 能用自己的话讲清数据流、规则、一次失败及修复、局限 |

你不需要做的：逐行学习所有代码；自己写样板；记住语法细节。
你不能交出去的：验收条件是什么；一个结果是否可信；对局限的陈述。

### 4.2 每阶段的理解检查

每阶段结束时花 3–5 分钟，回答 1–2 个问题（下面是每阶段最少的那一个）。答不出来就让 Claude 用一个具体例子再讲一遍；仍然不行，说明这一步做得太大，拆小。

| 阶段 | 你要能回答 |
|---|---|
| 0 | 这个交付支持什么决策？什么情况下它算做错了？ |
| 1 | 指着样例输入和期望输出：每个字段从哪来、给谁用？ |
| 2 | 一个输入依次经过哪几个函数？每个函数读什么、返回什么？ |
| 3 | 输入缺失或格式不对时，输出里会出现什么？为什么这样定？ |
| 4 | 哪个测试能证明核心规则是对的？把什么改坏，它会失败？ |
| 5 | 这个加分项如果没有，结论会差在哪？ |
| 6 | 干净环境里少了什么才会跑不起来？现在为什么不会？ |
| 7 | README 里每个数字来自哪条命令？ |
| 8 | 开发中遇到的一个真实错误：怎样发现的、原因、怎样修的、现在由哪个检查守着？ |

完整题库见[附录 C](#附录-c理解检查题库)。

### 4.3 每阶段的固定回路

```text

Claude：设计（输入输出、关键选择、会怎样失败）      ← 你在这里确认或修改
Claude：实现 → 运行 → 贴出命令与实际输出
Claude：一个反向验证（改坏或给坏输入，应当失败）
```

## 5. 常见阻塞与处理

先判断阻塞属于哪一类，再决定是换实现、用替身、还是缩范围。**在一个阻塞上超过 20 分钟没有进展，就停下来走这张表。**

| 阻塞 | 先试（各不超过 10 分钟） | 仍不行 | 最终交付里怎样处理 |
|---|---|---|---|
| 依赖安装失败 | 读完整报错；换题目指定的版本；用虚拟环境重装 | 换一个等价的库；或只用标准库实现最小路径 | README 写明实际使用的版本与安装命令；题目指定的依赖不能悄悄替换，换了要说明 |
| API 不可用（无密钥、限流、网络） | 确认密钥与额度；降低并发；加重试与退避 | 开发阶段用替身：脚本回放的模型、录制的响应 | 见下面的“替身与真实组件” |
| 模型表现差（真实模型大量失败） | 读 5–10 条失败轨迹，先排除环境、工具描述、判分的问题（[agent_harness 04](../../Knowledge/agent_harness/04_失败诊断与受控重跑.md)） | 确认是模型能力问题后，**不要为了好看去调判分** | 如实报告结果与失败分类；评估类题目里，“模型表现差”本身就是合法的发现 |
| 前端卡住 | 退到最简：单个 HTML、原生 JS、数据用 `<script>` 加载 | 改成命令行工具：文本时间线 + 筛选参数 | 题目明确要求界面时，交一个能用的最简页面，并说明没做的交互 |
| 数据格式不一致 | 先统计：有几种格式、各多少条、差在哪 | 只支持占多数的格式；其余记为无效并计数 | 报告里写明每种格式的数量与处理方式；不能悄悄丢弃 |
| 测试失败 | 先判断：是代码错、测试错、还是预期错？看具体输入输出 | 代码错就修代码；**不改测试来迁就代码**，除非你确认预期本身写错了，并记录原因 | 仍然失败的测试留在仓库里并在 README 说明，不删除、不跳过 |
| 环境里跑不了题目给的代码 | 确认平台要求（GPU、操作系统）；找最小可运行的子集 | 用只模拟接口的替身验证你写的逻辑 | 明确写出：哪些在真实环境运行过、哪些只在替身上运行过 |
| 时间不够 | 走 §3 的缩减顺序 | 再缩最小交付本身 | README 的“未完成”与“下一步”写具体 |

### 替身与真实组件

| 组件 | 开发时可以用替身吗 | 最终交付必须是真实的吗 |
|---|---|---|
| 模型调用 | 可以（脚本回放、录制的响应），用来验证接口与判分 | **题目要求真实模型运行时必须是**。替身的结果不能当作模型行为的证据 |
| LLM judge | 可以（预置标签） | 题目要求 judge 时必须接入；否则可以交确定性检查，并说明哪些标准没被覆盖 |
| 题目给的数据 | 可以先用一小部分开发 | **必须在题目给的全部数据上运行**，或写明跑了哪部分 |
| 题目给的被测系统／代码仓库 | 可以用模拟输出格式的替身测试你的包装逻辑 | 结论涉及它的真实行为时，必须真实运行过；否则只能说“逻辑在替身上验证过” |
| 外部服务（数据库、网络 API） | 可以用内存里的假实现 | 按题目要求；用了假实现要写明保真度的差距 |
| 判分与验证逻辑 | **不可以用替身**。它是交付的核心 | 必须是真实实现并有自己的测试 |

**何时缩范围**：阻塞在非核心部分（界面、第二种格式、加分项）；或者核心部分有一个更小但仍然端到端的版本。
**不能被替换的核心要求**：题目明文要求的产物与格式；判分或验证逻辑的真实性；在真实数据上运行；对“运行过什么、没运行过什么”的如实陈述。做不到时写明没做到，不要用替身的输出充当。

## 6. 交付与 code review 准备清单

### 6.1 提交前（阶段 6–9）

- [ ] **运行命令**：README 第一屏有安装与运行的命令；在干净目录里照着做过一遍
- [ ] **测试结果**：测试命令与最近一次的实际输出（通过数、失败数）贴在 README；失败的测试有说明
- [ ] **设计取舍**：3–5 条“我选了 A 而不是 B，因为 …”；每条你都能口头展开
- [ ] **已知限制**：没处理的输入、没验证的假设、结论的适用范围
- [ ] **实际运行过什么**：逐条列出，带命令。例如“在全部 N 条数据上运行了判分”“用真实模型跑了 K 次”
- [ ] **没有运行过什么**：逐条列出。例如“LLM judge 未接入”“Windows 未测试”“只在替身上验证了超时处理”
- [ ] **AI 使用说明**：按题目规则如实写（哪些由 AI 实现、你怎样审核与验证）
- [ ] 提交物的格式与题目要求一致；没有密钥、缓存、无关的大文件
- [ ] README 里的每个数字都能对上一条命令的输出

### 6.2 一条演示路径（5–8 分钟）

按这个顺序准备，每一步有一个能指着看的东西：

1. **问题与范围**（1 分钟）：支持什么决策；做了什么、没做什么。→ 指 README 的范围
2. **跑一遍**（1 分钟）：一条命令，看到结果。→ 终端
3. **数据流**（1.5 分钟）：一个具体输入经过哪些模块。→ 输入文件、中间落盘文件、输出
4. **规则**（1.5 分钟）：一条判定结果及其证据；判不了与出错怎么算。→ 一条检查结果
5. **一次失败及修复**（1.5 分钟）：现象、怎样发现、原因、修复、现在的守护检查。→ 反向验证的输出
6. **局限与下一步**（1 分钟）。→ README 的局限

### 6.3 code review 可能问到的

准备到能各用两三句话回答：

- 这个函数的输入输出是什么？最容易在什么输入上出错？
- 这条规则会误接受什么？会误拒什么？
- 你怎么知道测试本身是对的？
- 如果数据量大 100 倍，先坏的是哪里？
- 这部分是你写的还是 AI 写的？你怎样确认它是对的？（如实回答：谁写的、你看了哪些证据、做了什么反向验证）
- 再有一天，你先做什么？

## 7. 正式拿到题目后直接粘贴的执行 prompt

填好四个方括号后整段发给 Claude。

```text
我在做一个限时 take-home。请严格按下面的方式工作。

【题目全文】
<粘贴题目，包括交付要求与评分说明>

【剩余时间】
<例如：11 小时 30 分钟>

【运行环境】
<操作系统、Python 版本、有无 GPU、已有的依赖、题目文件所在的路径>

【允许使用的工具与规则】
<题目对 AI、联网、第三方库、模型 API 的规定；可用的 API 与预算；没有规定就写“题目未说明”>

工作方式：

一、先检查，不写代码。
1. 读题目全文，列出：硬性要求（逐条引用原文）、评分看什么、限制、不明确的地方。
2. 只读地检查项目与输入：目录结构、说明文件、数据的条数与格式与异常情况、给定代码能否运行、需要的依赖与凭据是否具备。
   给我一张数据概况表和一份环境检查结果。每个结论注明来自哪条命令或哪个文件。
3. 如果本仓库里有 Review/mirendil_takehome/执行指南.md，读它的 §2，告诉我题目最接近哪个方向，以及你建议复用哪个草图作为骨架。

二、然后提出最小验收与计划，等我确认。
4. 一句话的最小交付：输入什么、运行什么命令、得到什么、由什么证明正确。
5. 3–5 条“必须”验收，每条是可执行的检查；另列“加分”与“不做”（带理由）。
6. 按剩余时间给出分阶段计划：每阶段的产物、验收、时间；为调试、干净环境复跑、README、演示留出时间；
   写明进度落后时先砍什么。
7. 列出需要我决定的事项。我确认之前不要开始实现。

三、分阶段实现。每个阶段只做一件窄的事，并按这个顺序汇报：
8. 先用三五句话讲设计：输入输出、关键选择、可能怎样失败。等我回复“可以”再实现（我说“不用等”时可以直接做）。
9. 实现后运行，贴出：运行的命令、实际输出（过长时贴关键部分并说明省略了什么）。
10. 做一个反向验证：故意改坏被测逻辑，或给一个应当失败的输入，贴出它确实失败的输出；然后恢复。
11. 用一句话说明这个阶段的验收是否达成；没达成就说没达成和原因。
12. 给我 1–2 个理解检查问题，帮我确认我能解释这一阶段的关键设计。不要让我逐行读代码。
13. 记一行进度：完成了什么、证据在哪、已用时间、下一步。

四、关于证据的硬性规定。
14. 只把你在本次会话中实际执行过的命令的真实输出称为“运行结果”。
    没有执行的命令、你预期的输出、示例输出、替身或模拟的输出，必须明确标注为“未运行”“预期”“示例”或“替身”。
15. 开发中可以用替身（脚本回放的模型、录制的响应、模拟接口的脚本），但每次使用都要说明；
    替身的结果不能表述为真实模型或真实系统的行为。题目要求真实组件的地方，最终必须接入真实组件，做不到就明确告诉我。
16. 测试失败时先判断是代码错、测试错还是预期错，并告诉我；不要为了通过而修改或删除测试，除非我确认预期本身写错了。
17. 遇到阻塞超过 20 分钟没有进展，停下来告诉我：卡在哪、试过什么、有哪些缩范围或替代的选项及其代价。
18. 遵守题目的规则。规则不明确的地方先问我，不要自行假设对我有利的解释。

五、收尾。
19. 在一个干净目录里按 README 从头运行一遍，报告结果。
20. 起草 README：运行命令、设计与取舍、测试结果、已知限制、实际运行过什么、没有运行过什么、AI 使用说明。
    然后逐条核对：README 里的每个数字和每句“已验证”，对应哪条命令的输出；对不上的标出来。
21. 给我一条 5–8 分钟的演示路径，以及 code review 时可能被问到的问题和我应该怎样如实回答。

现在从第一部分开始。
```

### 附录 C：理解检查题库

按主题挑与本题相关的问。答案应当是两三句话，并能指着一个文件或一段输出。

**数据流**
- 一个输入从读入到产出结果，依次经过哪些模块？
- 中间落盘了哪些文件？只凭这些文件能不能重新得到结果？
- 哪个字段去掉以后，哪个功能会坏？

**规则与判定**
- 什么算通过？什么算失败？判不了和出错各算什么？
- 举一个会被误接受的输入、一个会被误拒的输入。
- 判定依据的是被测对象的自述，还是独立的证据？
- 规则由谁、在什么时候执行（执行前拦截，还是事后判定）？

**验证**
- 哪个测试守着核心规则？把什么改坏它会失败？
- 测试的期望值从哪来？会不会是照着实现的输出抄的？
- 什么都不做（空输入、空输出）会得到什么结果？

**结果的可信度**
- 结果的统计单位是什么？有多大的不确定性？
- 无效或缺失的样本怎样计入？
- 你读过几个具体样本？它们支持你的结论吗？

**取舍与局限**
- 为什么选这个切口？被砍掉的里面最可惜的是哪个？
- 哪些部分只在替身上运行过？
- 哪个结论你最没把握？需要什么才能确认？
