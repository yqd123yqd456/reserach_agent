# 口述稿与自测

> 用法：口述稿是**底稿**，请改成你自己的话。只使用任务文件第 2 节中有依据的经历；未补齐口径的数字（69%、72%、25M+ 等）默认不报。自测题先闭卷回答，再对照参考要点。

## 通用背景（基于任务文件 §2.8）

**30 秒**：
> I'm an Applied Scientist II at Microsoft on a centralized evaluation team for Copilot and Office agents. I build the evaluation workflows: trace normalization, rubric-based judging, and failure analysis. I've also fine-tuned smaller evaluator models from stronger-model labels. The question I care about is when an evaluation signal is trustworthy enough to drive improvement.

**90 秒**：在 30 秒版后补三点：
1. 系统侧：不同产品 agent 的 endpoint 和 tool schema 一直在变，我们用通用数据契约把 request、response、trace 和 telemetry 接到同一流程，任务的成功标准仍由各任务自己定义。判分时规则和语义 judge 分层使用。能看到最终 artifact 时直接检查它；看不到时，feedback 这类信号只当 proxy，不当作 outcome。
2. 模型侧：用较强 judge 的标签蒸馏出小 evaluator，在 held-out 数据上与 teacher 的一致率约 88%。这是对 teacher 的一致率，不是对人类的准确率。
3. 改进侧：从生产失败和 judge 分歧中挖出难例，产出偏好数据和回归集；与 modeling 团队合作做受控实验。训练基础设施由他们负责。

## Mercor Post-training RE

**30 秒**：
> My work sits between evaluation and post-training: I turn production failures into preference data and regression sets, and I've trained smaller evaluators myself. For this role, the question I'd focus on is which evaluation signals are safe to put into a reward, and how to show a data change improved the model rather than the judge's score.

**90 秒要点**：GRPO 只从组内分数差异中学习，难度校准因此也是 reward 设计的一部分；DAPO 的四项修改分别解决什么问题；judge 当 reward 的过优化风险（Gao）和作弊证据（METR、ImpossibleBench）；证明数据有效需要哪些对照（随机数据、随机 reward、跨模型族、评估与筛选分离）。

**深入追问自测**：
1. G=4、reward 为 (1,0,0,0) 时，各样本的 advantage 是多少？如果是 (1,1,1,1) 呢？这对 reward 设计意味着什么？
2. 为什么 DAPO 不用学习型 reward model？
3. 你蒸馏的 judge 若直接当 RL reward，最先担心什么？怎样监控？
4. 随机 reward 也让分数涨了 20 点，你怎么解释？下一步做什么实验？

<details><summary>参考要点</summary>

1. 总体 std：+1.73、−0.58、−0.58、−0.58；全对时全为 0。只有“有时对、有时错”的 prompt 产生梯度，所以要做难度筛选或 dynamic sampling。难题上 verifier 的假阳性会被大幅强化。
2. 为了避免 reward hacking，DAPO 改用规则判等（+1/−1）。
3. 难题上的假阳性；policy 分布漂移后的鲁棒性；被 game 的方式。监控方法：保留 gold 抽检；proxy 与 gold 的差距随训练的变化（Gao）；作弊率单独统计。
4. 参考 Spurious Rewards：增益可能来自截断偏差放大了预训练已有的行为，并依赖模型族。下一步：换一个模型族重复；加格式 reward 对照；分析增益具体来自哪类行为。
</details>

## Mercor Enterprise Evals Platform MTS

**30 秒**：
> I've built the data and judging layer of a centralized agent evaluation platform: shared contracts across products, trace normalization, and judge orchestration. What I'd bring here is the discipline of separating what the platform verified from what it inferred, plus a habit of testing the verifiers themselves before trusting a ship decision.

**90 秒要点**：从一条 run 讲起：task、环境重置、工具与 policy、trace、verifier（隔离运行，读状态不读自述）、valid 与 success 分开。然后讲 verifier 怎样验证：oracle、no-op、等价解、对抗 agent。再讲失败怎样变成回归测试。最后讲 rollout gate：回归集全部通过，保留集上配对差的区间，违规率不升，成本在约束内。

**深入追问自测**：
1. 为什么 τ-bench 曾经可以被“什么都不做”的 agent 拿到高分？
2. Terminal-Bench／Harbor 为什么在 agent 运行结束后才上传测试？
3. infra 错误应计为失败吗？
4. fixer agent 在验证集上反复迭代，会出什么问题？

<details><summary>参考要点</summary>

1. 航空域约 38% 的任务被设计为不可解，成功条件是“环境不变”，所以 no-op 也能通过（ABC）。
2. 防止 agent 读取或修改测试；判分前还会删除残留的 reward 文件。
3. 不计为失败，记为无效 run，单独报告数量和原因。资源设置本身会改变成功率（Anthropic 在 Terminal-Bench 2.0 上的结果）。
4. 验证集会退化成开发集。需要一个 fixer 看不到的冻结测试集用于最终 gate，并对 verifier 本身做对抗测试。
</details>

> I've done failure analysis on production agent traces for years: building taxonomies, mining disagreements, and feeding findings into data and regression sets. Last round we discussed classifying a failed rollout; what I'd add now is how I'd turn that classification into evidence, with a controlled rerun and a conclusion whose confidence matches the sample size.

**90 秒要点**：诊断五步，配一个具体例子（[Knowledge/04 §2](../../Knowledge/agent_harness/04_失败诊断与受控重跑.md#2-诊断流程一个完整例子教学假设未运行)）；怎样不依赖唯一的标准轨迹；judge 与人类的校准；失败模式的占比怎样报（写明分母，按任务聚类）。

**深入追问自测**：
1. 给你一条失败 rollout，前三步具体看什么？
2. 用户模拟器出错时怎么归因？
3. 你说 B 比 A 高 3 个点，可信吗？还需要什么信息？
4. 怎样衡量 tool use 能力，而不只是 JSON 合法率？

<details><summary>参考要点</summary>

1. valid／termination；终态与 verifier 证据是否一致；等价解是否被误拒。然后才找最早的偏离。
2. 单列为一类；抽样人工复核；必要时换成脚本用户重跑。τ² 报告的模拟器关键错误率为 6–13%。
3. 需要：任务数与簇数、配对差的区间、资源和预算是否一致、有效 run 数。Anthropic 建议对 3 个点以下的榜单差距保持怀疑（在他们的设置下）。
4. 五层：选择、参数、时机、解释、恢复；主指标是终态加过程约束；用负例任务。
</details>

## Resolution Scalable Oversight RS

**研究身份（30 秒）**：
> I work on making evaluation signals trustworthy enough to guide model improvement. In production I've seen how easily a judge's proxy can drift from the outcome it is meant to track. Scalable oversight is the version of that problem I find most important: what happens when the system being judged is stronger than the judge.

**Why alignment**（必须换成你自己的真实经历。下面是结构，不是现成答案）：
1. 一个具体的时刻：你发现 judge 或 proxy 的分数提升了，真实质量却没有提升。
2. 这个问题随模型变强会变得更糟：如果被优化的对象比评估者更强，它可能学会说服评估者，而不是变得更正确（Wen et al. 在 RLHF 中观察到这种现象）。
3. 所以你想研究：怎样在评估者更弱的情况下，仍然得到可信的信号。

**Why Resolution**：理论与实证的组合，加上研究自动化。launch 文章提出了 debate 的均衡可达性问题，这是实证研究能回答的一部分。JD 明确鼓励大量使用 AI 工具，同时小心不被它们骗过，这和你在评估工作中的习惯一致。

**两个研究问题与实验**：见 [Companies/Resolution §3](../../Companies/Resolution.md#3-第一轮15-分钟准备重点) 与 [Knowledge/09 §4](../../Knowledge/agent_harness/09_scalable_oversight实验设计.md#4-三个可证伪的小实验提案未运行)。练习用 60 秒讲完其中一个：问题 → 四个臂 → 固定预算 → 指标 → 证伪条件 → 不能推出的结论。

**深入追问自测**：
1. Khan et al. 和 Kenton et al. 对 debate 的结论为什么不完全一致？
2. 你蒸馏 judge 的经验和 scalable oversight 有什么关系，又有什么本质区别？
3. 怎样把“judge 更准”和“模型更会说服”分开测？
4. 你的小实验成功了，能说明什么，不能说明什么？

<details><summary>参考要点</summary>

1. Khan 主要在信息不对称任务上（QuALITY、judge 看不到原文、有引用工具）；Kenton 覆盖更多任务，发现封闭任务上收益很小或没有，debate 也不如有原文的 QA，而且 judge 与辩手同一模型时 debate 更差。
2. 有关系：都要测 judge 的准确率和校准，都会遇到标签噪声。区别：蒸馏时有一个可信的 teacher，scalable oversight 的问题恰恰是没有。
3. 指定立场并对称运行，分别算正确方和错误方的胜率；在“两版都错”的子集上算假阳性率（Wen）；盲评；用 gold 优化作对照；judge 用不同模型族。
4. 能说明：在该任务、该预算、推理时，这个协议帮助弱 judge 的程度。不能说明：训练时的效果、能力差距（而非信息差距）下的效果、对欺骗性模型的效果、均衡是否可达。
</details>
