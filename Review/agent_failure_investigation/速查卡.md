# agent_failure_investigation 速查卡：拿到题后怎样开工

> 配套：[Knowledge/agent_failure_investigation](../../Knowledge/agent_failure_investigation/README.md)、[Practice/agent_failure_investigation](../../Practice/agent_failure_investigation/README.md)。

## 开工顺序

1. **先自己读 10–20 条失败 rollout**，记下看到的失败类型与你是靠什么证据判断的。这决定分类法和工具。
2. **代码先行**：结构化摘要；任务 × 模型通过率表；能用规则判的先判（环境错误、参数被拒、超预算）。
3. **定结论 schema**：类别、根因、run 列表、证据（run、位置、原文引用）、竞争假设、待执行验证、状态（含“不确定”）。
4. **写引用校验器**，再让 agent 上场。校验失败的结论不进报告。
5. **给 agent 只读工具与固定预算**，只让它处理规则判不了的部分。
6. **建评估集**：预置故障、无故障对照、有噪声的成功 run、模糊样本、重复根因。分开报告证据有效率、分类的精确率与召回率、误报、重复、人工工作量。
7. README：workflow、工具、评估结果、哪些结论需要人确认、没有测什么。

## 必须能回答的问题

- 这条结论的证据在哪？代码怎样确认它不是编的？
- 你怎么知道助手漏了什么？
- 它把多少正常的 run 报成了失败？
- 证据不足或两种解释都说得通时，它输出什么？
- 哪些步骤用代码、哪些用 LLM？为什么？
- 报告里的“失败类别占比”，分母是什么？
- 用了它以后，人少读了多少？质量有没有下降？

## 常见错误

- 让 agent 直接读全部 trace 然后写总结，没有引用、没有校验。
- 只在被标记的样本上核查（只有精确率）。
- 没有对照组。
- 强迫给出确定类别。
- 同一根因报告多次，显得“发现很多”。
- 用结论条数或报告长度证明有效。
- 把观察到的共现写成原因，不给出验证动作。

## 自测（闭卷）

1. TRAIL 与 Who&When 的结果对设计调查助手意味着什么？
2. Inspect Scout 怎样保证模型引用的消息是真实存在的？
3. 为什么评估集里要有“成功但过程中有错误”的对照？
4. 引用校验通过，能说明结论正确吗？
5. 草图里有缺陷的那份结论，为什么“需要人读的 run 数”和合格的那份一样？这说明什么？

<details><summary>参考要点</summary>

1. 逐条细粒度归因准确率低，尤其在长 trace 上；聚合层面更可用。所以 agent 负责提出带证据的假设，确认交给代码与人；允许“不确定”。
2. 消息渲染时带序号标记；模型在解释中引用标记；代码用映射表把标记解析成真实 id，表里没有的直接丢弃；标记带随机 nonce 防止内容冒充。
3. 测误报：助手是否把与结果无关的错误当成失败原因。
4. 不能。它只说明引用的原文存在；原文是否支持结论需要人或另一轮核查。
5. 工作量代理只数要读的 run，不反映误归因与漏检。说明证据有效性、分类质量、工作量必须分开报告。
