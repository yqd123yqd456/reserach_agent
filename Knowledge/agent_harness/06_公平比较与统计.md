# 公平比较 model / prompt / skill / harness 变化

> 学习结论：比较的统计单位是**任务**，不是 run，也不是 step。先固定一切非干预条件（任务版本、verifier 版本、预算、资源、工具描述），再在同一批任务上做**配对差**，按任务族聚类计算不确定度。重复运行只能压低“同一题内的随机性”，压不低“题与题之间的差异”。
>
> 先修：[01 对象模型](01_三种harness与最小对象模型.md)。应用：[Practice L3 比较报告](../../Practice/agent_harness/00_共用harness规格.md#5-level-3多类任务故障注入诊断与比较报告)。

## 1. 一个例子：B 比 A 好吗？

16 个任务，每个任务 A、B 各跑 k=5 次。设任务 i 的通过次数为 `a_i`、`b_i`。

| task | a_i/5 | b_i/5 | d_i = b_i/5 − a_i/5 |
|---|---|---|---|
| t1 | 5/5 | 5/5 | 0 |
| t2 | 0/5 | 2/5 | +0.4 |
| t3 | 3/5 | 2/5 | −0.2 |
| … | … | … | … |

- **点估计**：`d̄ = mean_i(d_i)`。
- **为什么配对**：任务难度差异巨大（t1 两者都满分，t2 两者都很低）。如果把 A、B 当两个独立样本，难度方差会进入两边的 SE，掩盖真实差别。配对后题目难度在 `d_i` 里抵消。
- **配对 SE**（Miller 2024, §4.2）：`SE(d̄) = sqrt( Σ(d_i − d̄)² / (n(n−1)) )`，等价于 `sqrt(SE_A² + SE_B² − 2·Cov)`。A、B 在题目上的分数相关性越高，配对带来的收益越大。
- **聚类**：若 16 个任务来自 4 个任务族、族内高度相似，有效样本数接近 4 而非 16。应按族做 clustered SE（Miller 2024 §2.2；Inspect 的 `stderr(cluster=...)` 实现了带 `C/(C−1)` 有限簇校正的版本，并在簇数 < 2 时返回 0，见 `src/inspect_ai/scorer/_metrics/std.py`，commit `e4435ba`，已读代码未运行）。
- **重采样单位**：重采样的单位应与相关结构一致。任务之间独立、任务内重复 run 相关时，按**任务**重采样（每次抽中一个任务就带上它的全部 run 与 A、B 两臂的配对结果）；任务族内也相关时，按**族（簇）**整体重采样。Miller 的附录 C 也要求在簇层面重采样。
- **簇很少时**：bootstrap 不会自动解决小样本问题。只有 4 个簇时，簇级 bootstrap 只有很少种不同的重采样结果，区间往往偏窄、覆盖率不足；clustered SE 的正态近似同样不可靠。可行的做法：报告每个簇各自的配对差，让读者看到方向是否一致；用自由度为 C−1 的 t 分布给保守区间；明确写出“4 个簇，区间仅供参考”。真正的解决办法是增加独立的任务族。（簇很少时的这些问题属于统计学通识，Miller 原文未讨论簇数下限。）

## 2. 重复运行在做什么

Miller（arXiv 2411.00640）把估计量的方差拆成两部分：

`Var(μ̂) = ( Var(x) + E[σ_i²] ) / n`

- `Var(x)`：题与题之间“真实难度”的差异。
- `σ_i²`：同一题上模型输出的随机性。每题重复 K 次只把第二项变为 `σ_i²/K`。

**含义**：加大 k 提高“这道题是否稳定”的分辨率，但不能替代加任务。任务只有 16 个时，把 k 从 5 提到 50，区间仍然主要由 16 决定。Miller 还明确建议**不要靠降低温度来降方差**（那改变了被测对象）。

> 来源状态：公式经摘要工具读取，引用原文前应对照 PDF。

### pass@k 与 pass^k 回答不同问题

- `pass@k`：k 次里至少一次成功。适合“能否做到”（例如可以人工挑选、能重试的场景）。
- `pass^k`：k 次全部成功。适合“能否被放心交给它”。τ-bench 引入它衡量客服 agent 的一致性（见 [02](02_工具使用测量与过程约束.md)）。
- 简化直觉：若某题单次成功率为 p 且各次独立，`pass^k = p^k`（Anthropic 文中例子 0.75³ ≈ 42%）。**独立性是假设**：同一题的失败往往有共同原因（工具描述歧义），实际 pass^k 可能明显高于或低于 p^k，所以应直接用观测到的 k 次结果估计，而非由 p 推算。

## 3. 统计之外：最常见的“不公平”来源

| 混杂 | 例子 | 控制方法 |
|---|---|---|
| 资源／基础设施 | Anthropic（2026-02-05）在 Terminal-Bench 2.0 上只改资源上限：infra error 从 5.8%（1x）降到 0.5%（不设上限），成功率在不设上限时比 1x 高约 6 个百分点（p<0.01）；1x→3x 的成功率差在噪声内 | 两臂相同资源配置；把 infra error 计为无效 run 并报告；跨天分批 |
| 预算 | B 允许更多步／tokens | 固定预算，或报告质量–成本曲线 |
| 任务版本 | 中途修了 verifier | 任务和 verifier 带版本；只比较同版本 |
| 开发集泄漏 | 在 test 上调 prompt | dev 用于迭代；test 冻结、只在决策时跑 |
| 选择性报告 | 跑了 5 种 prompt 只报最好的 | 预先登记要比较的配置；多重比较时说明 |
| 工具描述 | B 的工具描述顺带修好了 | harness 改动与模型改动分开比较 |

### 3.1 无效 run 的判定不能用来排除失败

| 情况 | 归类 | 理由 |
|---|---|---|
| 供应商 API 429/5xx，adapter 重试后仍失败 | 无效，补跑 | 与 agent 行为无关 |
| harness 自身异常、环境未能启动 | 无效，修复后补跑 | 与 agent 行为无关 |
| 预算（步数、tokens、墙钟）耗尽 | **有效失败** | 预算是任务的一部分 |
| 工具错误超限、上下文溢出 | **有效失败** | agent 行为的后果 |
| agent 运行的代码导致 OOM 或磁盘写满 | 默认**有效失败**；若资源上限明显低于任务规格，属于环境配置问题 | 需要预先写进规则；Anthropic 的实验显示资源上限本身就会改变成功率 |
| 注入的故障 | 有效（这是实验条件） | — |

**防止通过排除失败夸大成功率**：规则在看结果之前定好；无效 run 补跑到每个任务有相同数量的有效 run，而不是直接丢弃；报告无效 run 的数量、原因及其在两臂之间的分布；无法补跑时，同时报告“排除无效 run”与“无效 run 计为失败”两种口径。无效 run 集中在某一臂或某类任务时，排除它们本身就会造成偏差。

Anthropic 的基础设施噪声文章（2026-02-05）建议对 3 个百分点以下的榜单差距保持怀疑。这是他们在该 benchmark 与资源设置下的经验，不是通用阈值。

## 4. 开发集、保留测试集、回归集各管什么

| 集合 | 作用 | 典型规模 | 失败代表什么 |
|---|---|---|---|
| dev | 快速迭代、看 trace、调 prompt/harness | 小、可频繁跑 | 正常，用于学习 |
| held-out test | 决策（发布／选择配置）时的独立证据 | 冻结，不用于调参 | 改动没有泛化 |
| regression | 已解决问题不再回退 | 接近 100% 通过 | 回退，阻止发布 |
| capability | 尚未解决的难题，衡量进展 | 起点通过率低 | 正常，衡量进展 |

Anthropic《Demystifying evals for AI agents》（2026-01-09）建议 capability 与 regression 分开，能力集“毕业”后转入回归集，并建议从 20–50 个来自真实失败的任务起步。20–50 适合发现问题，**不足以分辨小幅度改进**。Miller 的功效分析例子显示：要以常规显著性和 80% 功效检测 3 个百分点的差异，在其假设的方差下约需近千题。两者并不矛盾：前者讲起步，后者讲决策精度。

## 5. 功效：先算能看出多大的差别

Miller Eq. 10 的最小可检测效应（MDE）：

`δ = (z_{α/2} + z_β) · sqrt( (ω² + σ_A²/K_A + σ_B²/K_B) / n )`

**MDE 是规划量，不是检测下限**：给定显著性 α、功效 1−β 和假设的方差，MDE 是“有 1−β 的概率被检出”的最小真实效应。真实效应小于 MDE 时仍有可能得到显著结果，只是概率低于 1−β；而在低功效设计中，碰巧显著的估计往往高估真实效应。

实际用法：在只有 30 个任务时先算 MDE。若 MDE 是 15 个百分点，那么即使真实提升是 5 个点，这个设计多半检测不到；检测到时估计值也很可能被放大。报告应写成“该样本量下未检出差异（MDE≈15 点）”，而不是“没有差异”；若检出显著的 5 点，应提示低功效下估计可能偏大，并用更多任务复核。

## 6. 面试可能追问

- **“你怎么知道改进不是噪声？”** → 配对差 + 任务级区间 + 有效 run 计数 + 资源／预算一致性；说明 n 与簇数；必要时报 MDE。
- **“k 设多少？”** → 取决于要回答的是平均能力还是一致性；加 k 只降低题内方差。
- **“你把报错的 run 排除了，成功率会不会被夸大？”** → 见 §3.1：只排除与 agent 行为无关的原因，补跑而不是丢弃，并报告两种口径。
- **“pass^k 能用 p^k 算吗？”** → 只有在独立同分布假设下；直接用观测。
- **“你们的 production eval 怎么做 release gate？”** → 回归集必须过 + 保留集上的配对差及区间 + 违规率不升 + 成本约束。这对应 Mercor Enterprise Evals Platform JD 中的 release gate 要求（见 [Companies/Mercor](../../Companies/Mercor.md)）。
