# 失败诊断：从分类到证据，再到受控重跑

> 学习结论：你在 Mercor Benchmarking HM 面试中的三分类（environment/tooling、task/benchmark/grader、model capability）是好的起点。下一步是把分类变成证据链：**确认失败真实 → 找最早影响结果的偏离 → 提出竞争假设 → 受控干预 → 重跑 → 给出有置信边界的结论**。不要假定只有一条标准轨迹。
>
> 先修：[01](01_三种harness与最小对象模型.md)、[02](02_工具使用测量与过程约束.md)。相关：[05 verifier 验证](05_verifier的验证与防作弊.md)、[06 统计](06_公平比较与统计.md)。

## 1. 五类原因，以及区分它们的证据

把三分类展开成五类，因为“harness”与“grader”在修复归属上不同：

| 原因 | 典型表现 | 区分证据 | 修复归属 |
|---|---|---|---|
| 环境／基础设施 | 超时、OOM、服务不可用、容器崩溃 | 错误码出现在工具结果或 harness 日志；同配置下重跑消失；资源放宽后消失 | eval 平台 |
| execution harness | 工具描述误导、上下文被截断、参数校验把错误当崩溃 | 修改描述或上下文策略后，同一模型行为改变 | agent 团队 |
| 任务 | 指令有歧义、没有可行解、要求与 policy 冲突 | 人类专家（或 oracle 解）也无法按指令完成；多数模型在此题 0 分 | benchmark |
| grader／verifier | 正确结果被误拒、错误结果被接受 | 手工检查终态与 verifier 证据不一致；构造等价正确解被拒 | benchmark |
| 模型能力 | 在环境、任务、判分都正确时仍然做错 | 排除以上四类后，在受控重跑中稳定复现；在同类变体上也失败 | 训练／数据 |

**来自文献的提醒**：
- Anthropic（2026-01）建议把“大量试验都是 0%”视为任务很可能有问题的信号。
- τ-bench 作者在 gpt-4o 的 40 条零售失败轨迹中发现 4 条是指令笔误或歧义造成的。
- τ²-bench 的用户模拟器本身也会犯错：论文中关键错误比例为航空 13%、零售 12%、电信 6%。**有用户模拟器的 benchmark，第六类原因是“模拟用户出错”**。
- τ²-bench 的变更日志记录了 27 个航空任务与 26 个零售任务的修正，类别包括标准动作错误、指令歧义、约束不可能满足、policy 漏洞、缺少回退。

## 2. 诊断流程：一个完整例子（教学假设，未运行）

**任务** T1（[Practice/00](../../Practice/agent_harness/00_共用harness规格.md)）：验证身份后把 A2 地址改为 `9 New Ave`。
**观察**：5 次运行中 2 次失败，verifier 报告 `A2 address updated: False`。

### 第 1 步：确认失败真实

- 检查 `valid`：两次都是 `termination = final`，没有 harness 错误。
- 手工查看终态：A2 地址仍是 `1 Old St`。verifier 判对了。
- 检查 verifier 的等价解：如果 agent 写的是 `9 New Avenue`，是否应算对？任务定义说精确匹配，所以 verifier 无误。（若这里发现等价解被误拒，原因属于 grader，诊断到此结束。）

### 第 2 步：找最早影响结果的偏离

逐步看 trace 与状态 hash：

```text
step 0  find_customer("ana@example.com") -> c1             state h0
step 1  list_orders("c1") -> [A1(shipped), A2(processing)]  state h0
step 2  verify_identity("c1", "1234") -> ok                 state h1 (verified)
step 3  update_address("A1", "9 New Ave") -> BLOCKED: shipped  state h1
step 4  final: "抱歉，该订单已发货，无法修改地址。"
```

最早的偏离在 step 3：agent 选了 A1 而不是 A2。step 4 对 step 3 结果的解释本身是正确的（A1 确实已发货），所以这次不是“误读结果”，而是“选错对象”。

### 第 3 步：竞争假设

- H1（harness／工具描述）：`list_orders` 返回顺序让 agent 把第一个当成“目标订单”。
- H2（任务）：指令中订单号表述不清。检查指令：写明了 “A2”，排除。
- H3（模型能力）：模型在长上下文中丢失了订单号。

### 第 4 步：受控干预

每次只改一个因素，其他固定（同一模型、温度、预算、任务版本），每个条件重跑 k 次：

| 条件 | 改动 | 若 H1 成立，预期 | 若 H3 成立，预期 |
|---|---|---|---|
| C0 | 原样 | 约 2/5 失败 | 约 2/5 失败 |
| C1 | `list_orders` 返回顺序反转 | 失败模式变成“选 A2 正确”，失败率显著下降 | 失败率基本不变 |
| C2 | 指令中订单号移到句末 | 无显著变化 | 失败率变化 |

### 第 5 步：结论要带边界

例如：“在该任务、该模型、k=10 的重跑下，反转列表顺序后错选订单从 4/10 降到 0/10；结果支持 H1：agent 依赖列表位置而不是订单号。该结论只覆盖这一任务族；需要在其他‘列表后选择’的任务上验证。”

注意：**k 很小时，4/10 vs 0/10 的区间很宽**。结论应写成“支持”而不是“证明”，并说明下一步需要多少任务才能确认（[06](06_公平比较与统计.md) 的功效分析）。

## 3. 不要假定只有一条标准轨迹

- 用**终态与约束**判断成功，而不是与参考轨迹逐步对比。
- 找“最早偏离”时，偏离的参照是**状态与约束**（何时状态第一次变得无法挽回，何时第一次违反约束），而不是“与标准轨迹的第一处不同”。agent 走了另一条合法路径时，两条轨迹在第一步就不同，但并没有出错。
- 实际做法：从失败终态往回找，第一个让成功变得不可能（或代价大幅增加）的步骤，就是关键偏离。

## 4. 你在面试中提到的点怎样落到证据

| 你说过的点 | 落到证据 |
|---|---|
| 终态正确但过程违规 | 过程约束检查与违规率（[02](02_工具使用测量与过程约束.md)） |
| reward hacking | verifier 与 agent 隔离、作弊率单独统计、不可能任务对照（[05](05_verifier的验证与防作弊.md)、[07](07_从评估信号到post-training.md)） |
| 无界 sub-agent 成本 | 成本是任务预算的一部分；同时报告成功与成本；预算超限是独立的终止原因 |

## 5. 把诊断变成回归测试

Mercor Enterprise Evals Platform JD 原文：“对生产轨迹做 loss analysis，把失败模式变成回归测试”。Mercor 博客也写到，生产中失败的非阻塞 verifier 可以转成新的离线评估测试。最小流程：

1. 从失败 trace 中抽出**最小可复现条件**（fixture + 指令 + 必要的故障）。
2. 写成任务，带上能命中该失败的 verifier 检查。
3. 先确认当前版本在这个任务上失败（确认测试有效），修复后再确认通过。
4. 放入回归集（目标接近 100% 通过），并保留来源 trace 的链接。

## 6. 面试追问

- “给你一个失败任务和完整 rollout，你怎么找原因？” → 按第 2 节五步讲；强调先排除 grader 与环境，再谈模型。
- “怎么知道是模型能力而不是 harness？” → 受控干预：固定模型改 harness，固定 harness 换模型；看失败是否跟着因素走。
- “用户模拟器出错怎么办？” → 把模拟器错误单列为一类；抽样人工复核；必要时用脚本用户替代。
- “失败模式的占比怎么报？” → 分母是失败的 run 还是全部 run 要写明；按任务聚类；样本少时给区间。
