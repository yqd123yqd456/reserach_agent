# 工具使用怎样测：正确的工具、参数、时机、解释、恢复，以及过程约束

> 学习结论：tool-call JSON 合法率只说明“格式会写”。agent 的工具能力至少有五层：选对工具、填对参数、在对的时机调用（包括不该调用时不调用）、正确理解返回结果、失败后恢复。主指标应是**终态 + 过程约束**；分层诊断指标用来解释失败，不用来替代主指标。
>
> 先修：[01](01_三种harness与最小对象模型.md)。相关：[03 故障注入](03_故障注入与恢复.md)、[05 verifier 验证](05_verifier的验证与防作弊.md)。

## 1. 为什么只统计 JSON 合法率不够

例子（orders 环境，[Practice/00](../../Practice/agent_harness/00_共用harness规格.md)）：用户要求修改订单 A2 的地址。

| 轨迹 | JSON 合法 | 结果 |
|---|---|---|
| `update_address(order_id="A2", address="9 New Ave")`，没有先验证身份 | ✅ | 违反 policy |
| `update_address(order_id="A1", ...)` | ✅ | 改错订单 |
| `get_order("A2")` → 返回 `status: shipped` → agent 仍回复“已修改” | ✅ | 误读结果，并虚假声称完成 |
| 先 `verify_identity` → `update_address("A2")` → 告知用户 | ✅ | 正确 |

四条轨迹的格式全都合法，只有一条是对的。

## 2. 五层能力与各自的测法

| 层 | 问题 | 怎样测 | 典型证据 |
|---|---|---|---|
| 选择 | 是否调用了对的工具 | 必要动作是否出现；是否调用了不该调用的工具 | τ² 的动作检查：标准动作必须出现在轨迹中（按参数比较），不惩罚顺序和额外调用 |
| 参数 | 参数是否正确 | 与标准动作的参数比较；或直接看终态 | τ-bench 不直接比参数，参数错会体现在数据库 hash 不一致 |
| 时机 | 是否在前置条件满足后才调用；不该做时是否不做 | 过程约束（verify 在 write 之前）；负例任务 | AppWorld 给每个测试标注“什么都不做时会失败／会通过”，防止“什么都不做”被误判成功 |
| 解释 | 是否正确理解返回 | 回复内容与环境状态一致；不基于错误或过期数据行动 | τ-bench 检查回复是否包含必要信息（子串匹配） |
| 恢复 | 出错后是否合理应对 | 故障注入 + 配对的 clean control | 见 [03](03_故障注入与恢复.md) |

**主指标与诊断指标的关系**：主指标回答“任务是否完成且没有违规”。五层指标回答“如果失败，失败在哪一层”。只报告诊断指标（如“工具选择准确率 92%”）会掩盖“选对了工具但最终仍然失败”的情况。

## 3. 每题重置、允许多条合法路径、验证终态、检查过程约束

### 3.1 重置

| 做法 | 来源 |
|---|---|
| 每次评估从文件重新构造环境；回放轨迹重建状态 | τ²-bench：各领域的 `get_environment` 加载数据库，或深拷贝 |
| 每个任务一份数据库副本 + 冻结时钟 | AppWorld：`evaluate_task` 中设定本地日期时间 |
| 每次试验一个新容器 | Terminal-Bench |

练习中的最低要求：fixture 深拷贝；同一任务连续两次运行，初始状态 hash 相同。

### 3.2 多条合法路径

- **判终态**：τ-bench 只比较最终数据库，对话与只读调用可以自由变化。代价是每条指令都要写到“在领域 policy 下只有一个可能结果”。作者在验证阶段对每个零售任务跑了 40 次以上，并检查成功率为零或很低的任务。
- **允许集合**：AppWorld 用状态差异 Δ 判定：期望的变化 C_expect 必须全部出现（C_expect ⊆ Δ），且所有变化必须落在期望或允许的集合内（Δ ⊆ C_expect ∪ C_allow）。后一条就是**附带损害**检查。
- ABC 清单 O.g.1：标准答案应覆盖所有可达的成功状态；O.g.2：既检查相关状态，**也检查不相关状态**。

### 3.3 过程约束

终态检查发现不了“先写后验证”。τ-bench 作者明确说，奖励为 1 是“必要但不充分”的：例如没有用户确认就办理退货，终态可能仍然正确。处理方法：

1. **能在执行边界拦截的，用 policy 代码拦截**（写操作前检查 `verified`）。这样违规根本不会发生。
2. **需要评估 agent 是否“试图”违规的，在 trace 中检查**：被 policy 拦截的尝试是否算违规，要在任务定义中写明。
3. **不能自动判定的过程要求**（例如“语气礼貌”），用 rubric 和经过校准的 judge；它们是 rubric 检查，不是 policy。

policy 与 journey 要一起设计：先确定用户路径中哪些步骤不可逆，再在这些步骤前放 enforcement，而不是先实现完整流程再事后补检查。

## 4. 可靠性：pass^k

τ-bench 定义 pass^k 为“同一任务 k 次独立试验全部成功的概率，在任务间平均”。每个任务跑 n 次、成功 c 次时，无偏估计为：

`pass^k = E_task[ C(c, k) / C(n, k) ]`

对比 `pass@k = 1 − E_task[ C(n−c, k) / C(n, k) ]`。k=1 时两者相等。τ²-bench 在 `src/tau2/metrics/agent_metrics.py` 的 `pass_hat_k()` 中实现（n<k 时报错）。

例子：某任务 n=8、c=6。pass^1 = 0.75；pass^4 = C(6,4)/C(8,4) = 15/70 ≈ 0.21；pass@4 = 1 − C(2,4)/C(8,4) = 1（C(2,4)=0）。即“几乎总能做到一次”，但“连续 4 次都做对”只有约 21%。

τ-bench 报告 gpt-4o（function calling）在零售域 pass^1 为 61.2%，pass^8 低于 25%。

AppWorld 的场景级指标（SGC）是另一种一致性：同一场景的 3 个任务初始状态不同，三者都对才算对。报告中 GPT-4o + ReAct 在 Test-N 上任务级 48.8、场景级 32.1。

## 5. 面试追问

- “怎么测 agent 动态选工具的能力？” → 五层；主指标是终态 + 约束；负例任务测“不该调用时不调用”；工具数量与描述相似度作为难度变量。
- “参考轨迹比对有什么问题？” → 误拒合法路径；只能用作“必要动作是否出现”。
- “终态对了但过程违规怎么算？” → 判失败，并单独统计违规率；能拦截的在执行边界拦截。
- “Mercor 的 APEX-Agents 怎么判？” → 专家写的 1–10 条必须满足的标准加标准输出；judge 看提示、输出和变更日志，**不看轨迹**；在 747 条人工标签上报告 98.5% 准确率（Mercor 自报）。这是“判结果不判路径”的例子；报告的失败分析中也统计了 36 次不该发生的文件删除，属于附带损害。
