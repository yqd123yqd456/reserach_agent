# 故障注入与 recovery 评估

> 学习结论：recovery rate 不是一个数，而是一组**定义选择**：哪些故障算可恢复、分母是“所有 run”还是“真的遇到故障的 run”、恢复的成功是“最终完成”还是“正确应对”（含正确放弃）、成本怎样计。每个 faulted task 都需要一个配对的 clean control，否则无法区分“故障造成的损失”和“题本来就难”。
>
> 先修：[01 对象模型](01_三种harness与最小对象模型.md)。实现：[Practice L3](../../Practice/agent_harness/00_共用harness规格.md#5-level-3多类任务故障注入诊断与比较报告)。

## 1. 为什么要注入故障

真实 agent 面对的工具会超时、限流、返回错误、返回看似合法但错误的数据。只在干净环境里评估，测的是“顺风”能力。注入故障的目的是在**可控、可复现**的条件下测三件事：

1. agent 是否注意到出了问题（检测）。
2. 是否采取合适行动：重试、换路径、修正参数、或停止并如实告知（应对）。
3. 应对的代价：额外步数、tokens、副作用风险（成本）。

## 2. 故障分类：按“可恢复性”和“可见性”两个轴

ToolMaze（Zhu et al., arXiv 2606.05806, 2026-06）用 2×2 分类：**显式**（机器可读的异常，如 HTTP 404）vs **隐式**（结构合法但内容错误，如库存为负数），**暂时**（只在第一次调用失败，重试可成功）vs **永久**。摘要称在隐式语义故障下，其恢复指标下降约 37%（是相对还是绝对下降，读取时未确认）。

结合到练习环境：

| 故障 | 例子（orders 环境） | 可恢复？ | 正确应对 | 判定证据 |
|---|---|---|---|---|
| 暂时、显式 | `update_address` 第一次返回 503 | 是 | 重试（且写操作需幂等） | 最终状态正确；无重复写 |
| 参数错误 | 地址缺邮编被 422 拒绝 | 是 | 修正参数或向用户询问 | 修正后的调用成功 |
| 隐式、暂时 | `get_order` 第一次返回过期状态 | 部分 | 写前再次确认或交叉核对 | 不基于过期数据做写入 |
| 永久、显式 | 地址服务整体不可用 | 否 | 停止写入，如实告知，不声称已完成 | 状态未变 + 回复未声称成功 |
| 非幂等部分写 | 写入成功但响应超时 | 危险 | 先查询状态再决定是否重试 | 没有双写 |

**最后一行最值得在面试中讲**：盲目重试在只读调用上是对的，在非幂等写上可能造成损害。恢复评估必须同时看附带损害（[02](02_工具使用测量与过程约束.md)）。

## 3. 指标：分母是关键设计

设 faulted 条件下的 run 集合为 R，其中真正触发了故障的子集为 R_f（agent 可能根本没调用被注入的工具）。

| 指标 | 分子 | 分母 | 回答什么 |
|---|---|---|---|
| faulted success | 成功的 run | R | 有故障时整体能完成多少 |
| clean success | 成功的 run | clean control 的 run | 题本身多难 |
| **recovery gap** | `success_clean − success_faulted`（同任务配对） | 任务 | 故障让完成率损失多少 |
| **conditional recovery** | 触发故障后“正确应对”的 run | R_f | 遇到故障时应对得好不好 |
| graceful failure | 不可恢复故障下：未声称成功 且 无不安全写 | 不可恢复故障中触发的 run | 能否安全失败 |
| recovery cost | 额外步数／tokens 中位数（vs clean 配对） | 成功的 faulted run | 恢复代价 |

文献里的对应选择：

- **ToolMaze**：PRR 的分母只包括“故障被触发”的轨迹；“恢复”定义为重试、换路径、或对不可解任务正确中止，并且**与最终成功分开打分**；任务成功率（TSR）与恢复成本（RC）则在所有轨迹上平均。
- **AgentProp-Bench**（单作者，arXiv 2604.16706）也只在“注入调用被执行”的 trace 上算 recovery，但每个模型只有 2–45 个这样的 trace。这说明以触发为条件的指标**样本可能非常少**，必须报告分母。
- **Tian et al.（arXiv 2606.25819）** 不给形式化的 recovery rate，而是报告故障下的准确率，以及失败轨迹的模式分布：无效继续 48.6%、过早放弃 26.7%、利用不足 11.3%、答案综合失败 13.4%（基于 8,130 条失败轨迹）。他们的设计要求每个注入实例**至少保留一条有效恢复路径**，参考答案来自 clean 路径。

**取舍**：以触发为条件，不会惩罚“碰巧没走到故障工具”的 agent，但样本少、且条件本身可能与能力相关（更聪明的 agent 先调用别的工具）。以全部 run 为分母，则混合了暴露与恢复。实践中两者都报，并报告触发率。

## 4. 实验设计：最小合同

- **注入要确定性**：同一 (task, fault) 对每个模型施加相同故障（ToolMaze 的做法），否则不同模型面对的条件不同。
- **记录故障是否真的触发**：写进 `Step.fault`。没有这个字段，conditional recovery 无法计算。
- **clean control 配对**：同一任务、同一 agent 配置、同样 k。
- **预先定义“正确应对”**：例如永久故障下“告诉用户稍后再试且不声称完成”算正确；“改用另一个未授权工具完成”可能违反 policy，算违规而非恢复。
- **成本**：重试次数上限是 harness 参数还是 agent 行为？若 harness 自带自动重试，测到的是 harness 的恢复，不是模型的恢复。两者都可以测，但要分开报告。

## 5. 一个完整例子（教学假设，未运行）

任务 T1（改 A2 地址），注入：`update_address` 第一次调用返回 503（暂时、显式）。

- run 1：agent 收到 503 → 再次调用 → 成功 → 告知用户。判定：成功，已恢复，成本 +1 步。
- run 2：agent 收到 503 → 回复“已为您修改” → 结束。判定：失败（状态未变，且虚假声称完成）。这比单纯失败更严重，应单独统计为“false success claim”。
- run 3：agent 收到 503 → 调用 `get_order(A2)` 看是否已写入 → 发现未写入 → 重试 → 成功。判定：成功；这是非幂等场景下更稳健的策略，成本 +2 步。

只看“成功率”，run 1 与 run 3 相同；只看“成本”，run 1 更优。若把同一故障改成“写入成功但响应超时”，run 1 的策略会造成双写或重复操作，run 3 才是正确的。这个对比可以直接作为面试中“recovery 怎么定义”的回答。

## 6. 面试追问

- **recovery rate 的分母是什么？** → 两种都报，并给出触发率；说明为什么。
- **怎样确保恢复不是 harness 自动重试造成的？** → harness 重试关闭或单独记录；trace 中区分 harness retry 与 agent retry。
- **哪些故障不该恢复？** → 永久故障、权限拒绝、policy block：正确行为是安全失败。
- **故障注入的结论能推广吗？** → 只适用于注入的故障分布、任务和预算；真实故障分布需要从生产日志估计。
