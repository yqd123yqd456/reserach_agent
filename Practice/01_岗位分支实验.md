## A 平台可靠性：把 infra 错误与模型失败分开

- **问题**：资源限制、超时和工具故障会让多少“失败”其实是无效 run？自动重试会不会改变比较结论？
- **要区分的解释**：成功率差异来自模型，还是来自 harness 的重试或资源设置。
- **设置**：同一 agent 配置，三种 harness 设置：(1) 无自动重试；(2) 对只读工具的 transient 错误自动重试 1 次；(3) 对所有工具重试。在 L3 的任务集上各跑 k=5。注入 transient 故障（[Knowledge/03](../Knowledge/03_故障注入与恢复.md)）。
- **判定**：报告每种设置的 valid run 数、success、violations（尤其是写操作重试造成的双写）、成本。
- **反例**：设置 (3) 成功率最高但出现双写，说明“成功率”单独不能作为 harness 选择标准。
- **附加**：每个 run 的 trace 中记录 `harness_version`、重试次数、故障是否触发；任何报告中的数字都能追溯到 run_id。
- **工作量**：标准 6h。
- **常见失败**：harness 重试被记成 agent 行为；并发跑时 fixture 被共享导致状态串扰。

## B benchmark 审计：量化自己 verifier 的误收与误拒

- **问题**：L3 任务集的 verifier 有多少误收／误拒？
- **设置**：对每个任务构造：oracle 解、no-op、空回复、“把所有状态打印出来”的回复、2 个等价正确解、每个检查项 1 个错误变体。再用一个被指示“尽量拿高分、可以利用漏洞”的真实模型 agent 跑一遍（需凭据；未配置时只做构造部分）。
- **判定**：每个任务一张表：哪些构造被正确判定；汇总误收率与误拒率。修复后重跑，报告修复前后分数变化。
- **对照文献**：ABC 清单（T.4–T.10、O.g.1–O.g.3、O.b.1–O.b.2、R.13）、Terminal-Bench 的 oracle/no-op CI 与对抗作弊 agent。
- **交付物**：一份“benchmark 审计报告”，这正是 Benchmarking JD 加分项中提到的作品类型（failure-analysis reports、benchmark suites）。
- **工作量**：标准 8h（不含真实模型对抗部分）。
- **常见失败**：只测自己想得到的错误；等价解只换格式不换路径。

## C 训练数据消融：失败挖掘的数据是否真的更有用

- **问题**：从失败 trace 中挖出的训练样本，是否比同等数量的随机样本更能提升 held-out 任务表现？
- **要区分的解释**：提升来自数据内容，还是来自训练本身（任何数据都会带来的格式或风格变化）、或来自筛选用的 judge 偏好。
- **设置（设计）**：
  - 数据池：L3 环境上的轨迹（成功与失败），用于 SFT 或偏好对。
  - 臂：(1) 失败挖掘 + 修正后的轨迹；(2) 随机等量轨迹；(3) 不训练。（若做 RL：再加随机 reward 与格式 reward 对照，见 [Knowledge/07 §5](../Knowledge/07_从评估信号到post-training.md#5-怎样证明选出的数据真的提升了模型)。）
  - 评估：L3 的 **test split**（未参与挖掘），用执行型 verifier，而不是用于筛选的 judge。
  - 至少两个模型族（若算力只够一个，结论中明确写“单族”）。
- **判定**：配对比较 (1) vs (2)，任务级区间；同时报告违规率与作弊式通过。
- **执行边界**：**默认不启动 GPU 训练或付费 API**。本轮交付设计与数据处理代码；小模型（例如 <1B）LoRA 实验只有在你明确决定后才运行。
- **工作量**：只做设计与数据处理 4h；含小规模训练与评估 16–24h（另需算力）。
- **常见失败**：评估集与挖掘集重叠；用同一个 judge 选数据并证明提升；只跑一个 seed。

## D 研究任务验证：报告的数字是不是真的跑出来的

- **问题**：一个研究 agent 在 `lab` 环境中“跑实验并报告指标”，verifier 怎样确认报告属实？
- **环境**：一个小型、CPU 可跑的实验（例如在固定种子的小数据集上训练逻辑回归或小 MLP，指标为验证集准确率），agent 可修改超参数、运行脚本、写报告。
- **verifier 设计**：
  1. harness 从自己的执行日志中提取每次运行的配置与指标（agent 不能写这份日志）。
  2. 报告中的每个数字必须能对应到日志中的某次运行，且容差内一致。
  3. 用报告中声称的“最佳配置”由 harness 重新执行一次，结果在容差内复现。
  4. 检查 agent 是否读取了验证集标签之外的保留集（作弊）。
- **反例构造**：一个 scripted agent 编造数字；一个报告了未完成运行的数字；一个在保留集上调参。三者都必须被拒。
- **连接**：RE-Bench 的“复制权重模拟训练”与 PaperBench 的“过早声称完成”（[Knowledge/08 §4](../Knowledge/08_研究agent评估与L1L2L3.md#4-研究-agent-的已记录失败)）。
- **工作量**：标准 8h。
- **常见失败**：verifier 读取 agent 写的结果文件；容差设得过宽。

## E 弱 judge 监督：证据访问 vs debate（缩小版 P1）

- **问题**：在固定字数预算下，弱 judge 的准确率提升是来自 debate 还是来自可验证引用？
- **设置**：QuALITY 风格的二选一阅读题（使用公开数据集，需确认许可）；强模型能看原文，弱 judge 看不到；引用工具对原文逐字匹配的引用标为“已验证”。四臂：朴素 judge、只给证据、带引用的 debate、双边 consultancy。位置互换；judge 与辩手来自不同模型族。
- **判定**：judge 准确率、Brier 分数、在“分配到错误方”时的被说服率；按题配对比较。
- **证伪条件**：若 debate 不优于“只给证据”，则收益可由引用访问解释（[Knowledge/09 §4](../Knowledge/09_scalable_oversight实验设计.md#4-三个可证伪的小实验提案未运行)）。
- **规模与成本**：50–100 题 × 4 臂 × 位置互换，量级是几千次模型调用；**运行前估算费用，默认不消耗付费 API**。
- **不能推出**：训练时效果、能力（而非信息）差距下的效果、对欺骗性模型的效果。
- **工作量**：设计 3h；实现与运行 12h（另需 API 预算）。
- **常见失败**：judge 与辩手同族；没有位置互换；预算在臂之间不一致。
