# Research Application

将研究结论变成可理解、可检验的行为。可独立使用，不要求先完成完整文献调研。

## 请求

$ARGUMENTS

确认要具体化的机制、使用场景、已有基础、约束和期望产物；未知项用合理假设标注。相对链接以本文件所在目录为准。

按需读 [内容质量](../topic-research/references/content-quality.md)、[来源与验证](../topic-research/references/evidence-and-verification.md) 和 [内容参照](../topic-research/references/golden-examples.md) 中相关片段。

## 选择最合适的形式

| 用户需要 | 交付重点 |
|---|---|
| 理解定义或公式 | 小输入、逐步计算、数值变化、含义与假设 |
| 理解系统 | 一条完整路径、状态变化、接口输入输出和错误分支 |
| 选择方案 | 决策标准、baseline、条件变化与取舍 |
| 验证研究主张 | 可反驳假设、数据、干预、对照、判定与局限 |
| 独立练习 | 题目、验收、分级提示与分开的参考答案 |

不因为 topic 涉及系统就搭大项目；也不因为已有示例代码就把用户要求的完整实现降格为伪代码。

## 设计实验

先写清“要区分哪两种解释”，再选最小设置。说明：

- 数据与初始状态如何构成，哪些是合成，哪些来自实际任务。
- Baseline、干预、预算、重复运行单位和需要固定的条件。
- 预期观察与可能反驳主张的结果，避免事后只解释支持性证据。
- 成功、失败、无效运行与约束违规怎样判定；排除规则先定义并报告数量。
- 一个有区分力的反例和必要的正常回归检查。
- 与真实系统相比保留了什么机制、简化了什么、下一步需要什么证据。

指标必须有明确分子、分母和适用范围。评测数据与调参数据分开；比较时固定相关预算，或者明确报告质量与成本的权衡。

## 执行与验收

用户要求实现或运行时，在授权范围内完成最小实现、运行和必要诊断；发现问题后修复并重测相关部分。缺算力、工具或依赖时，先完成不受阻部分，说明阻碍和可直接执行的下一步。不能把生成代码、静态阅读或语法检查写成实验成功。

选择能暴露错误的检查：手算对照、独立参考、输入变形、不变量、负例或受控干预。避免只用当前实现自己生成的答案验证自己。

练习题与解答分开。闭卷练习需要新输入或变体；“看过”和“独立通过”分别记录。不要因为用户问了一个问题就推断其整体能力不足。

## 输出

按需要交付计算过程、数据示例、组件设计或代码文件，并给出检查方法。若实际运行，附配置、观察结果与实质限制；若仅提案，明确标注“未运行”。接回真实场景时说明可迁移的机制和未验证的差距。

对于用户项目，仅用已提供的经历建立联系；新方案不能写成用户已做过的工作。
